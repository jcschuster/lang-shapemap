# codemirror-lang-shapemap

[ShapeMap](https://shex.io/shape-map/) language support for
[CodeMirror 6](https://codemirror.net/): a Lezer parser generated from the grammar (section 6)
of ShapeMap Structure and Language, Draft Community Group Report 13 July 2017 (recorded in
`package.json` under `shapemap.specification`), with highlighting and completion of `FOCUS`
and `START`.

```js
import {EditorView, basicSetup} from "codemirror"
import {shapemap} from "codemirror-lang-shapemap"

new EditorView({extensions: [basicSetup, shapemap()]})
```

`shapemap()` returns a `LanguageSupport`; `shapemapLanguage` is the `LRLanguage`.

Nodes are named after the productions of the report (`ShapeMap`, `ShapeAssociation`,
`NodeSelector`, `TriplePattern`, `ShapeLabel`, `Predicate`, `RdfLiteral`, ...) and tokens
after its terminals (`Iriref`, `PnameLn`, `AtStart`, `LangStringLiteral2`, ...); `FOCUS`,
`START`, `_`, `{` and `}` are tokens named by their text. Comments are `LineComment`. IRI,
prefixed-name and literal nodes have the same names and highlighting as in
[codemirror-lang-shex](https://github.com/jcschuster/lang-shex), with one difference in
structure: the datatype after `^^` is the `Iri` child of `RdfLiteral` here, where
codemirror-lang-shex has a `Datatype` node around it.

What the tests show: every production and terminal of the report, as amended by the two
deviations below, is reachable from a top rule of the grammar (`BLANK_NODE_LABEL`, which no
production uses, only from the top rule `Unused`, so that `_:b` is an error); each token
matches what the report's terminal matches on samples generated from the terminal and edits
of them; the test cases and the valid fixtures contain every node type but `Unused`; the
report's Example 3, hand-written maps and rudof's example maps parse without errors, and
the shex.js ShapeMap parser accepts them all. Text outside the grammar, such as status
`@!`, reasons, JSON appinfo, `SPARQL "…"` selectors, a trailing comma or blank nodes, which
shex.js accepts, gets error nodes.

Two deviations from the report, listed in `spec/README.md` of the repository: `a`
(rdf:type) as the predicate of a triple pattern instead of a subject term, as in the
editor's draft, which the report's own Example 3 needs; and prefixed names, also directly
after `@` (`<n>@ex:S`). Where the report's longest-match rule and shex.js read text
differently, this grammar follows the report (`spec/README.md`, "Ambiguities"): `FOCUS:x`
is a prefixed name, `_:b` a blank node label that no production takes, and `"chat"@START`
and `"chat"@ex:S` are strings with the language tags `START` and `ex`, so errors, which
shex.js reads as a string and a shape label. Completion therefore offers no `START` right
after a string and its `@`.

## Generated and hand-written files

In the [lang-shapemap](https://github.com/jcschuster/lang-shapemap) repository:

- Generated: `spec/shapemap-2017.ebnf`, extracted from the report by `gen/fetch.mjs`, and
  `src/shapemap.grammar`, generated by `gen/ebnf2lezer.mjs` (`pnpm generate`) from it,
  `spec/deviations.ebnf` and `gen/overlay.grammar`.
- Hand-written: `spec/deviations.ebnf`; `gen/overlay.grammar` (the top rule, the hidden
  and unused productions, the skip rule, the punctuation tokens; each entry explained in
  `gen/CONFLICTS.md`); `src/highlight.ts`, `src/index.ts` and `src/shapemap.grammar.d.ts`.
